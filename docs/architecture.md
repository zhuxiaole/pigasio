# 架构说明

这份文档解释 PigASIO 为什么是现在这个样子。如果你想改引擎的行为,
应该先读这里。

## 核心问题:ASIO 只有一个时钟

ASIO 宿主和驱动之间的契约是「同步双缓冲」:驱动按固定周期调用
`bufferSwitch(index)`,宿主在这个回调里读输入、写输出。**这个周期本身
就是时间基准** —— 所有通道的数据必须在同一个时间轴上对齐。

FlexASIO 能满足这个契约,是因为它只开一条 PortAudio 流,而
`Pa_OpenStream()` 恰好接收「一个输入设备 + 一个输出设备」。此时
两个设备共享同一个回调周期,时间轴天然统一。

一旦要支持多设备,这个前提就没了:每块声卡都有自己的晶振。标称
48 kHz 的两块声卡,实际频率可能相差几十到几百 ppm。如果不处理,
偏差会线性累积 —— 100 ppm 意味着每 10 秒差 48 帧,约 3.5 分钟就差出
一个 1024 帧的缓冲区,然后就是爆音。

## 解法:主从时钟 + 水位反馈

```
                         ┌─────────────────┐
     时钟主设备回调 ──────▶│   AudioCore     │
     (硬件时钟)           │                 │
                         │  buffers:       │  ASIO 双缓冲
                         │  inputs:  [...] │  每流的 ring 读端 + 重采样器 + 控制器
                         │  outputs: [...] │
                         │  callback:      │  宿主的 bufferSwitch
                         └────────┬────────┘
                                  │
                 ┌────────────────┼────────────────┐
                 │ 从设备回调线程  │                │ 从设备回调线程
                 ▼                ▼                ▼
           只碰自己的 ring 另一端(完全无锁)
```

**主设备**:配置里选一个设备作为时钟主设备(默认第一个输出设备)。
它的设备回调是唯一触发 `process_one_buffer()` 的地方,所以 ASIO 的
时间轴就等于主设备的硬件时钟。

**从设备**:每个从设备都有独立的环形缓冲和变速重采样器。控制器
观察环形缓冲的水位,不断微调重采样比率,让水位稳定在目标值上。
水位稳定就意味着生产速率和消费速率匹配 —— 也就是从设备的时钟
被软锁到了主设备。

### 控制律

两个方向用的是同一个公式:

```
修正量 = -(Kp * e + integral)      其中 e = (当前水位 - 目标水位) / 目标水位
```

方向之所以能统一,是因为重采样比率的定义在两个方向上恰好互补:

| | 重采样比率 | 水位偏高时减小比率的后果 |
|---|---|---|
| 输入流(设备→ASIO) | `ASIO率 / 设备率` | 每次 ASIO 处理消耗更多设备帧 → 水位回落 |
| 输出流(ASIO→设备) | `设备率 / ASIO率` | 每块 ASIO 数据产出更少设备帧 → 水位回落 |

两个方向都是「减小比率 → 水位下降」,所以共用一套控制器。

**为什么必须要有积分项**:持续存在的时钟偏差要求持续存在的非零修正量。
只有比例项的话,水位稳定在目标值时误差为零、修正量也为零,偏差会立刻
重新累积。积分项正是用来提供这个稳态修正的。

**为什么需要两档上限**:积分项的上限(来自 `max_drift_ppm`)只需要覆盖
真实漂移,几百 ppm 就够;而启动时水位可能离目标差好几个缓冲区,用
几百 ppm 去补要几十秒,这段时间系统一直贴着欠载边缘跑。所以比例项
另外有一个更宽的上限(`total_limit`,默认是前者的 10 倍且不超过 0.5%)。
0.5% 的比率偏移约等于 8.6 音分,短暂出现基本听不出来 —— 比持续爆音好得多。

## 线程模型

### 设备流必须在专用线程上

`cpal::Stream` **不是 `Send`**。它在 Windows 上持有裸 `HANDLE`,在别的
平台上是 `PhantomData<*mut ()>`。而 ASIO 引擎必须能被宿主的任意线程访问。

所以 `Engine` 把「创建 / 启动 / 停止 / 销毁设备流」全部收拢到一个专用
线程(`pigasio-streams`),自己只保留一个命令通道。`crates/pigasio-core/tests/send_probe.rs`
用编译期断言把这个约束钉住了 —— 如果哪天有人把 `cpal::Stream` 直接塞回
`Engine`,那个文件会编译失败。

### 锁的边界

`AudioCore` 的锁只在两处出现:时钟主设备的回调,以及 `start`/`stop`
这类控制接口。后者在音频运行期间几乎不发生。

**有一条硬性约束**:任何可能在 `bufferSwitch` 内部被宿主调用的 ASIO 接口
(`getSamplePosition`、`outputReady`)**绝不能**去拿这把锁。宿主完全可能
在自己的 `bufferSwitch` 处理里回头调用它们,而 `parking_lot::Mutex` 不可
重入 —— 那会直接死锁。这两个接口读的是 `DriverObject` 上的原子字段,
由音频回调直接维护。

### 启动顺序

`Engine::start()` 的顺序是精心安排的:

1. 把宿主预先填好的输出缓冲(ASIO 约定是 index 1)推进输出环形缓冲;
2. **只启动输入流**,让它们开始采集;
3. 等输入环形缓冲攒到目标水位(最多 300 ms);
4. **启动输出流** —— 此时输出环形缓冲里已经有第 1 步放进去的数据;
5. 打开回调闸门,开始正常的缓冲区交换。

如果第 1 步之后就启动全部流,输出设备会在采集设备还没送来任何数据时
就开始跑,宿主第一次要读输入缓冲时那里是空的。

第 3 步的门槛必须按**目标水位**而不是「重采样器下一次需要多少」来定。
只预热到刚好够一次 `fill()` 的话,环形缓冲立刻见底,等设备送来下一批
数据之前就欠载了。这个坑是在真机上踩出来的:水位从 2.0 提到 3.0 才
把开场欠载压到零。

## ASIO 接口的特殊之处

ASIO 不是规矩的 COM:

1. 宿主从 `HKLM\SOFTWARE\ASIO\<名字>\CLSID` 读到驱动的 CLSID;
2. 调 `CoCreateInstance(CLSID, ..., riid = CLSID, ...)` —— **把 CLSID 当 IID 用**;
3. 把拿到的 `void*` 直接盲转成 `IASIO*`,从不调用 `QueryInterface`。

后果有两个:

* 驱动对象的**第一个字段必须是 `IASIO` 的虚表指针**,否则宿主取到的
  函数地址全部错位。`DriverObject` 的 `repr(C)` 布局和 `IASIO_VTBL`
  一起保证了这一点。
* `QueryInterface` 收到自己的 CLSID 时必须返回自身。

`crates/pigasio-asio/src/abi.rs` 里有专门的测试用字段偏移把虚表顺序
钉死。虚表顺序错一个字,宿主不会编译失败,而是直接跳到错误的函数上。

## 一些刻意的取舍

### 不支持 `bufferSwitchTimeInfo`

那个回调要求驱动构造 `ASIOTime`。而 `ASIOTimeCode` 在官方头文件的
`#pragma pack(4)` 下是 84 字节,在 Rust 的自然对齐下会被补齐到 88 字节
(因为它含 `f64`)。布局不一致意味着宿主的栈会被写坏。

避免这个陷阱最省事的办法就是干脆不声明支持 —— 驱动不在
`asioMessage` 里询问 `kAsioSupportsTimeInfo`,宿主会自动退回
`bufferSwitch`。代价是宿主拿不到时间码,对常规录音回放没有影响。

### 只支持 64 位

ASIO 在 32 位下用 MSVC 的 `__thiscall` 调用接口方法,而 Rust 稳定版
无法表达这个调用约定。64 位下所有调用约定统一,`extern "system"`
就是正确答案。

### 只暴露 float32

它也是 Windows 音频引擎的内部格式,共享模式下几乎总是可用,而且
省掉一次格式转换。设备侧倒是支持 f32/i16/i32/u16 四种格式(见
`engine.rs` 里的 `build_input` / `build_output`),因为它们会被统一
转成 f32 再进引擎。

### 环形缓冲存交错数据

设备回调拿到的就是交错数据,可以直接整块搬运。把通道重排的代价推迟到
ASIO 侧 —— 那里本来就要做 deinterleave 才能喂给重采样器。

### 缓冲指针必须稳定

`AsioBufferSet` 每个通道一块**连续**内存,前半段是 index 0,后半段是
index 1。宿主会长期持有这些指针,任何重新分配都会让它手里的指针失效,
进而踩坏宿主进程的内存。所以内部缓冲一旦建立就不再重新分配。

## 数据流走一遍

以「2 块输出设备 + 1 块输入设备」为例,一次 `bufferSwitch` 里发生的事:

```
宿主写入 ASIO 输出缓冲[index]
        │
        ▼
AudioCore::process_one_buffer()
        │
        ├─▶ 对每个输入流:
        │     从 ring 读 ≈N 帧 → 重采样成 N 帧 → 写 ASIO 输入缓冲[channel_map]
        │
        ├─▶ callback(index)          ← 宿主在这里读输入、写输出
        │
        ├─▶ 对每个输出流:
        │     读 ASIO 输出缓冲[channel_map] → 重采样成 ≈M 帧 → 写 ring
        │
        └─▶ 对每个流:
              读水位 → 控制器算出修正量 → set_relative_ratio(1 + 修正)
```

设备回调那一侧则简单得多:

```
输入设备回调: cp.lab buffer 拆交错 → 写 ring → (如果是主设备) advance()
输出设备回调: 读 ring → 转格式 → 写 cpal buffer → (如果是主设备) advance()
```

## 目录结构

```
crates/pigasio-core/src/
├── config.rs      TOML 配置解析与校验
├── devices.rs     设备枚举与「名字片段/正则」匹配
├── ring.rs        每流一个的无锁 SPSC 环形缓冲
├── resample.rs    rubato 封装 + 交错/分离通道转换
├── drift.rs       PI 控制器
├── engine.rs      多流生命周期 + 时钟主设备驱动
└── error.rs       错误类型

crates/pigasio-asio/src/
├── abi.rs         ASIO SDK 2.3 的 ABI 类型翻译 + 虚表布局断言
├── driver.rs      IASIO 实现
├── factory.rs     IClassFactory 实现
├── registry.rs    COM 与 ASIO 驱动注册表
└── lib.rs         DLL 导出
```
